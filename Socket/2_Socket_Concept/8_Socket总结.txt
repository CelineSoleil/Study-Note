<********************************>群聊
小明键盘: "大家好"
  → A主线程 send(fd_A)
    → 内核TCP① → 服务器线程① recv 返回
      → 拼前缀 "小明: 大家好"
      → broadcast: 加锁遍历 map，跳过 fd_A
        ├→ send(fd_B) → 内核TCP② → B的receiver线程 recv → 打印 "小明: 大家好"
        └→ send(fd_C) → 内核TCP③ → C的receiver线程 recv → 打印 "小明: 大家好"

<********************************>私聊
小明键盘: "@小红 在吗"
  → A主线程 send → 服务器线程① recv
    → 解析: text[0]=='@' → 目标="小红" 内容="在吗"
    → private_chat: 加锁遍历 map 找 name=="小红" → 找到 fd_B →没找到重新输入名字，close连接
      ├→ send(fd_B, "[私聊] 小明: 在吗")     → 只有小红看到
      └→ send(fd_A, "[你私聊 小红] 在吗")     → 小明收到回执
    （小刚的连接 fd_C 全程没被碰到）

<********************************>下线
小明 quit（或关终端）
  → A的main: shutdown(fd_A)        （关终端则由内核代发 FIN）
    → 服务器线程① recv 返回 0 ← "对方走了"的唯一信号
      → close(fd_A)
      → 加锁 erase(map)
      → broadcast(-1): "小明 离开了聊天室，当前在线 2 人"
        → B、C 的 receiver 线程打印通知



问：TCP保证了什么？
1.可靠送达，数据丢了会重新传，端到端，每个字节都有序号，对方返回ack就完成，超时未返回重新发
2.按序到达，发123不会收到321，序号排序，乱序的包先缓存在拼接
3.流量控制，滑动窗口，会告诉对方我还能收多少，收了多少
4.面向连接，通信前先建立专线，三次握手建立，四次挥手关闭

不保证：
1.不保证消息边界——TCP 是"字节流"，像水管不是像快递盒。
    发”abc“和”def“可能是”abcdef“（粘包）也可能是”ab“，”cdef“（拆包）
        TCP 眼里根本没有"一条消息"，只有一串字节。
2.不保证”发送成功==对方收到“
    send 返回成功只代表数据交给了本机内核的发送缓冲区，不代表到了对方，更不代表对方程序读了。
        所以"发送失败"只能在后续操作中才发现。
3.不保证立刻发现对方死亡
    对方正常 quit（四次挥手）你的 recv 会返回 0；
        但如果对方是拔网线/断电，没有 FIN 包，你的 recv 会一直阻塞，
        可能几分钟到几小时后才发现（靠 TCP keepalive 或应用层心跳）。这叫"半开连接"。

TCP 给的是"可靠的、有序的字节流管道"，但"什么算一条消息"和"对方还活着吗"是应用层自己的事。

问题：
1.服务器的 server_fd 和 accept 返回的 client_fd 各管什么？为什么不能 accept 完就 close server_fd？
2.为什么 clients 这个 map 要配 mutex？不加会发生什么、什么时候发生？
3.为什么离开时要先 erase 再 broadcast，顺序反了会怎样？
4.recv 返回 0 和返回 -1 含义有什么不同？
5.为什么需要 send_all 循环，直接一次 send 不行吗？
6.快速连发两条消息，对方为什么可能一次收到？（用"字节流"三个字回答）
7.对方拔了网线，你的服务器多久能发现？为什么？

1.fd 是连接/通道的句柄，server_fd负责开门，连接客户端，accept的client_fd是发送数据的；
    因为断开后，我只连接了一个客户端，要保持服务器打开才能一直连接。
2.因为clients这个map是多个线程都会碰，必须要原子性，mutex锁住对clients的操作，同一时刻只准一个线程进临界区，把"同时碰"变成"排队碰"。
    如果不加代码运行顺序会变，导致内容更新不及时，交叉破坏。
3.先erase保证广播列表里没有死连接，这是为了防止"通知发给错误的陌生人
4.0表示连接断开正常关闭，四次挥手，-1表示接收失败，报错
5.因为一次性可能发不完，所以我们要循环检查判断，发送字节是否等于消息长度，循环发送。
6.因为TCP是字节流管道，只保证字节可靠、有序，可能导致俩次消息粘包成一条，也可能会拆包导致俩条消息不同于原消息。
7.发现不了，因为我没写，TCP也发现不了，需要应用层自己判断，如写时钟判断。
